Background & goal

AN AGENT THAT ACTS IN THE REAL WORLD

Pine is a personal AI assistant that gets things done by acting — it places real phone calls to negotiate your bills, books appointments, fills forms, and drives a computer to finish multi-step jobs. Unlike a chatbot, its output is not an answer; it is an outcome in the real world.

The core tension

DELEGATION ANXIETY IS THE REAL CEILING

The more capable the agent becomes, the less the user can see — and the more it feels like losing control. Every task handed to Pine is an act of trust: money, appointments, personal data. Delegation anxiety, not capability, is the real adoption ceiling.

Analysis · how trust forms around an agent

TRUST IS BUILT — OR LOST — ACROSS THE TASK LIFECYCLE

I mapped user anxiety across the three stages of delegating a task to Pine. Each stage has one dominant question in the user's head, and one failure mode that destroys trust. These three questions became the backbone of every design decision that follows.

Stage 1 · Delegate

“What exactly is it about to do?”

Failure mode: the blind hand-off — user submits a task into a void and immediately regrets it.

Design answer → set expectations before execution: task cards state the goal, the plan and what Pine may need from you.

Stage 2 · Execute

“What is it doing right now?”

Failure mode: the black box — minutes of silence while an AI makes calls with your name on them.

Design answer → continuous visibility: thinking states, live progress, and a real-time window into every action.

Stage 3 · Deliver

“What did I actually get?”

Failure mode: the unverifiable claim — “done!” with nothing the user can check or keep.

Design answer → structured proof: summaries, artifacts and next steps the user can verify and reuse.

Three questions → three design goals: SEE IT · STEER IT · GET IT

Strategy 1 · See it

MAKE THE AGENT'S WORK VISIBLE — AT THE FIDELITY YOU CHOOSE

Visibility is not one component — it is a system of altitudes. A glanceable status for the 95% of the time users don't care, and a full live window for the moments they do. Two surfaces carry this: thinking states in chat, and the Computer Use view.

A · Thinking states — reasoning you can glance, not a wall of logs

Collapsed by default — one calm line signals “I'm working”, no cognitive tax.

Tap to expand — the live step list, for users who want to follow the reasoning.

Done — thinking folds into a compact trace; the answer stays the hero.

Why collapsed by default

Trust needs calm, not spectacle. Showing every token of reasoning reads as noise and makes errors louder. Progressive disclosure keeps confidence high and cost low.

B · Computer Use — a window, not a log

When Pine drives a real computer, users deserve to watch. I designed one truth at three altitudes — the same live session, progressively disclosed. Read-only by design: you can always look, and the playback scrubber lets you rewind any step.

L1 · Glance

Banner in chat — one line + live thumbnail. Enough to know it's running.

L2 · Monitor

Bottom panel — live screen, step 4/5, thinking timer, playback controls.

L3 · Inspect

Full screen — the whole session, scrubbable like a recording.

The ladder rule

Every level answers one question and offers exactly one step deeper. Glance → Monitor → Inspect. No level dead-ends; no level forces the next.

Iteration · showing the model's mind, twice

WE SHIPPED THE WRONG TRANSPARENCY FIRST

Chain-of-thought is a double-edged surface. Our first experiment streamed the model's full reasoning into chat — maximum transparency, catastrophic experience. The iteration taught us that trust comes from legible reasoning, not visible reasoning.

V1 · Experiment

Full reasoning, always expanded. Users read every token — hesitations amplified, hallucinated sub-steps became visible promises, and reading cost grew with model verbosity.

→
Shipped

One calm summary line, expandable on demand. The model's verbosity no longer taxes the user; transparency became a choice instead of a burden.

What this taught us about LLM UX

Model output length is not under the designer's control — the UI must be. Any surface bound to raw generation inherits its variance. Summarise by default; disclose by intent.

The first principle · why these patterns exist at all

Voice for the gist,
UI for the rest.

Pine's bet: voice is the highest-bandwidth way into a computer — you speak roughly 4× faster than you type, and tone and urgency come for free. But the way back is different. Reading beats listening for anything dense, exact, or private. So the product is not “a voice assistant” — it is a multimodal loop, and my job was to design the half that voice can't carry.

🗣
Talk to decide

Discussion, options, judgment. Voice keeps the conversation flowing — the gist, not every detail read back aloud.

👆
Tap to confirm

Exact constraints — a booking time, a hard no-go window — become a scannable card. You tap through the spec instead of reciting it.

⌨
Type in private

An SSN or password must never land in the voice channel. Pine stops you mid-sentence and opens a secure typed field instead.

Fast thinking
Keeps the conversation flowing

Real-time, low-latency. Tracks pauses, hesitation, interruptions, back-channels — the live voice loop.

Slow thinking
Gets things done

Runs alongside: plans, retrieves, calls tools, manages long tasks — surfaced as the screens in this study.

Strategy 2 · Steer it

HAND THE WHEEL BACK AT THE MOMENTS THAT MATTER

Full autonomy is not the goal — earned autonomy is. I designed five human-in-the-loop patterns, each placed exactly where a wrong move would be irreversible: personal data, standing permissions, and identity verification.

P1 · Structured ask

In-chat forms — when Pine needs your details it asks once, structured and inline, instead of an interrogation over ten messages.

P2 · Approval gate

Need-action cards — routines pause and wait for an explicit human sign-off before anything runs on your behalf.

P3 · Human handoff

Three-way verification — when a bank insists on a human, Pine dials you in for the sensitive moment, then takes the call back.

P4 · Send review

Outbound email review — nothing leaves in your name without your eyes on it first.

P5 · Scoped access

Connecting Google Calendar — permissions asked in context, scoped to the task, never a blanket grant.

The interruption policy — when does Pine stop and ask?

Interruptions are spent like a budget. One policy decides every pause — designed once, applied everywhere.

Pine needs to act → Reversible · in-scope · low-stakes? YES → Act autonomously — and log every step
NO ↓   what is at stake?
Needs your personal data→P1 · Structured ask — an inline form, once
Moves money or makes a commitment→P2 · Approval gate — explicit sign-off
Institution insists on a human→P3 · Human handoff — three-way call
Speaks in your name (email, messages)→P4 · Send review — you see it before it leaves
Touches a connected account→P5 · Scoped access — permission in context
The pause rule

Pine only interrupts when regret would be irreversible: money moves, identity, standing permissions. Everything else keeps flowing — interruptions spent like a budget.

Strategy 3 · Get it

END EVERY TASK WITH PROOF, NOT A PROMISE

An agent's word is worthless without receipts. The result system bookends every task: expectations are set in a structured card before execution, and every run ends in a record the user can verify, keep, and act on.

R1 · Kickoff

Task card at start — goal, plan, and what Pine may need. Expectations before execution.

R2 · Task summary

One structured record per task — what was done, what changed, what's next.

R3 · Call record

Every call ends in an auditable to-do trail — outcomes become checkable items.

One state machine

New → Started → In progress → Done → Continue. One card family carries the task through every state — users learn it once, then read every task at a glance.

R4 · Cross-surface — the same result system scales to desktop web

Principles · what conversational AI demands from design

FOUR RULES I NOW DESIGN BY

01

Design for probability, not the happy path

LLM output is a distribution, not a result. Every surface needs a “partially right” state — confidence framing, editable results, graceful correction — not just success and failure.

02

Latency is a material

Streaming tokens, thinking states, elapsed timers: pacing is to AI products what typography is to print. We design the wait, not just the answer.

03

Context is the real UI

What the model remembers (the Notebook), what it is allowed to touch (scoped access) and what it forgets shape user trust more than any single screen.

04

Failure is a first-class flow

Misheard calls, wrong forms, refused requests — repair paths (edit, retry, escalate to human) get the same design care as the golden path, because they carry the most trust weight.

Beyond features · reflection

WHAT DESIGNING FOR AN AGENT TAUGHT ME

Systems, not screens

THE QUIET WORK

Alongside features I maintained the icon library, upgraded the button component family, and kept chat spacing rules consistent across sprints — the quiet work that makes 100+ screens feel like one product.

Status is the product

FEEDBACK IS THE CORE LOOP

In agent UX, feedback design is not polish — it is the core loop. Users don't evaluate the model; they evaluate what they can see of it. The status system is the product.

Design the pauses

WHEN NOT TO AUTOMATE

The hardest decisions were about when NOT to automate. Choosing where the agent stops and asks turned out to matter more than any single screen.
